HTTP не защищён. Любой, кто может перехватить трафик, увидит пароль.

HTTPS шифрует данные. При использовании HTTPS вы бы увидели только TLS-рукопожатие, а содержимое было бы зашифровано.

🎯 Kerberoasting – успешная атака
Цель: Получить хеш билета Kerberos для учётной записи службы и попытаться взломать его офлайн.

Выполненные шаги:

На контроллере домена (Windows Server, IP 10.10.10.200) создана учётная запись svc_sql с паролем SvcP@ss2026!.

Для этой учётной записи настроены SPN (Service Principal Names):

HTTP/sql.cyberlab.local

MSSQL/sql.cyberlab.local

С Kali (IP 10.10.10.100) с использованием утилиты GetUserSPNs.py из набора Impacket запрошен билет Kerberos для svc_sql.

Получен хеш вида $krb5tgs$23$*..., сохранён в файл hash.txt.

Запущен John the Ripper для взлома хеша:

bash
john --wordlist=/usr/share/wordlists/rockyou.txt hash.txt --format=krb5tgs
Пароль SvcP@ss2026! не был найден в стандартном словаре, что подтверждает: слабые пароли легко взламываются, а сложные требуют времени или других методов.

Результат: Атака Kerberoasting выполнена успешно. Получен хеш, который можно использовать для офлайн-взлома или для дальнейшего продвижения по сети (например, Pass-the-Hash).

🛡️ Детекция в Wazuh
Во время атаки Wazuh зафиксировал событие Event ID 4738 (изменение учётной записи), связанное с svc_sql. Это показывает, что SIEM может отслеживать изменения в AD, но для обнаружения Kerberoasting необходима настройка правил на Event ID 4769 (запрос билета службы Kerberos). Такое правило уже добавлено в локальную конфигурацию Wazuh.

Вывод: Wazuh способен детектировать атаки на AD при правильно настроенном аудите и правилах корреляции.

📊 Итоги дня
EternalBlue не сработал — Windows 10 защищена. Это нормально, в реальных условиях не все уязвимости приводят к успеху.

Kerberoasting отработан полностью: от создания SPN до получения хеша и попытки взлома.

Wazuh зафиксировал события, связанные с изменением учётных записей, что подтверждает важность мониторинга AD.
